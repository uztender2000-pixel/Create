# Marketplace Backend — мультипостачальницька версія

Бекенд маркетплейса: тягне каталоги кількох постачальників, зводить їх в один
каталог, приймає замовлення й автоматично розкидає їх по постачальниках.

## Що змінилось порівняно з попередньою версією

Раніше система була жорстко прив'язана до одного постачальника: `products.id`
був ID оферу з фіду dropshipping.ua, а замовлення відправлялись одним хардкодженим
HTTP-запитом. Тепер:

| Було | Стало |
|---|---|
| `products.id` = ID оферу постачальника | власний числовий `id`, а `(supplier_id, supplier_product_id)` — унікальна пара |
| один постачальник із `.env` | таблиця `suppliers`, керується через API без редеплою |
| один жорсткий формат замовлення | адаптери: свій модуль на кожного постачальника |
| роздріб затирався при кожному синку | ручна ціна захищена прапорцем `price_overridden` |
| зниклі з фіду товари продавались вічно | після синку неоновлені товари йдуть в `available = false` |
| `GET /api/orders` відкритий усьому інтернету | закритий адмін-авторизацією |
| `PATCH /api/products/:id/retail-price` відкритий | закритий адмін-авторизацією |
| 1 INSERT на товар у циклі | батчі по 500 через `UNNEST` |

### Виправлений баг, що з'їдав націнку

У старому імпортері в `ON CONFLICT DO UPDATE` стояло `retail_price = EXCLUDED.price`.
Тобто щогодини роздрібна ціна затиралась закупівельною: виставив 379 грн — через
годину знову 200 грн. Тепер ціна, виставлена вручну, ніколи не перезаписується,
а решта товарів переціновується за націнкою постачальника.

## Архітектура

```
routes/            HTTP-шар
services/
  catalogSync.js      синхронізація каталогів усіх постачальників
  orderDispatcher.js  розбиває замовлення по постачальниках і відправляє
  suppliers/
    index.js          реєстр адаптерів
    ymlFeed.js        адаптер XML/YML-фідів (dropshipping.ua та будь-які інші)
```

Одне замовлення клієнта = один `group_id` і кілька рядків у `orders`, по одному
на товар. Кожен рядок знає свого постачальника. Диспетчер групує рядки за
постачальником і відправляє кожному тільки його частину.

## Як додати нового постачальника

**Якщо в нього звичайний XML/YML-фід** — коду писати не треба:

```bash
curl -X POST https://твій-домен/api/admin/suppliers \
  -H "Authorization: Bearer <admin-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "newsupplier",
    "name": "Новий постачальник",
    "adapter": "yml_feed",
    "feed_urls": ["https://example.com/feed.xml"],
    "markup_percent": 30
  }'
```

Далі запустити перший імпорт:
`POST /api/admin/suppliers/:id/sync`

**Якщо у нього власний API** (BRAIN, MTI) — потрібен новий адаптер:

1. створити `services/suppliers/brain.js` за контрактом, описаним у
   `services/suppliers/index.js`
2. додати рядок `brain: require('./brain')` у `ADAPTERS`
3. створити постачальника з `"adapter": "brain"`

Більше нічого в коді не змінюється: `catalogSync` і `orderDispatcher` працюють
з будь-яким адаптером однаково.

## Міграція існуючої бази

Відбувається автоматично при першому старті нової версії. Скрипт:

- реєструє dropshipping.ua як першого постачальника
- дає кожному товару власний числовий id, старий зберігає в `supplier_product_id`
- перепривʼязує `orders.product_id` і `cart_items.product_id` на нові id
- товари, у яких роздрібна ціна відрізнялась від закупівельної, позначає
  `price_overridden = true`, щоб не втратити виставлені вручну ціни

Дані не втрачаються, замовлення не втрачають звʼязок із товарами. Скрипт
ідемпотентний: повторні запуски нічого не ламають.

**Перед деплоєм зробіть бекап бази** (Render → PostgreSQL → Backups).
Міграція протестована, але резервна копія за 30 секунд — дешева страховка.

## Нові ендпоінти

### Постачальники (потрібен дозвіл `settings`)

| Метод | Шлях | Що робить |
|---|---|---|
| GET | `/api/admin/suppliers` | список із кількістю товарів і станом останнього синку |
| GET | `/api/admin/suppliers/adapters` | які адаптери підтримує ця збірка |
| POST | `/api/admin/suppliers` | додати постачальника |
| PATCH | `/api/admin/suppliers/:id` | змінити налаштування |
| POST | `/api/admin/suppliers/:id/sync` | запустити імпорт зараз |
| POST | `/api/admin/suppliers/:id/reprice` | перерахувати ціни за націнкою |
| DELETE | `/api/admin/suppliers/:id` | видалити (блокується, якщо є замовлення) |

`api_key` ніколи не повертається назовні — тільки прапорець `has_api_key`.

### Замовлення (потрібен дозвіл `orders`)

| Метод | Шлях | Що робить |
|---|---|---|
| GET | `/api/admin/orders/groups` | замовлення так, як їх робив клієнт: одне на чекаут |
| GET | `/api/admin/orders/groups/:groupId` | усі позиції одного чекауту, згруповані по постачальниках |
| POST | `/api/admin/orders/groups/:groupId/retry/:supplierId` | повторити відправку одному постачальнику |
| GET | `/api/admin/orders?failed=true` | тільки ті, що не пішли постачальнику |

### Каталог

`GET /api/products?supplier=code` — фільтр по постачальнику.
Вимкнення постачальника (`active: false`) миттєво ховає весь його каталог.

## Автоматичне замовлення

У постачальника є прапорець `auto_order`:

- `false` (типово) — замовлення зберігається, приходить Telegram, ви оформлюєте
  вручну в кабінеті постачальника. Це поточний робочий процес.
- `true` — диспетчер сам відправляє замовлення через адаптер.

Збій API одного постачальника ніколи не ламає замовлення: рядок лишається
збереженим, отримує `supplier_status = 'failed'` з текстом помилки, Telegram
приходить у будь-якому разі, а в адмінці є кнопка повтору.

## Локальний запуск

```bash
npm install
cp .env.example .env    # вставити DATABASE_URL, JWT_SECRET, ADMIN_JWT_SECRET
npm run dev
```

## Що варто зробити далі

  щоб показувати один товар із вибором найдешевшого постачальника
